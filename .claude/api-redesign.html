calbot API redesign

From a Telegram bot's workflow to a food-logging API three different clients can build on.

The one idea. Right now, logging food requires the food to exist first. You send an input string, the server searches, you pick a match, you log the match. That is the same gate FatSecret puts in front of you, re-implemented — and it is the thing you said annoys you most.

Invert it: an entry carries its own nutrition. You can log 230 kcal with 31 g of protein, named whatever you like, in one call, having searched nothing. The food database becomes an accelerator for things you log often, never a precondition for logging at all.

Everything below follows from that inversion, plus the fact that the current auth scheme only works for a Telegram client.

What's wrong today

The API was shaped by one client, so it ships that client's decisions. Three kinds of problem, in order of how much they block you:

Only Telegram can authenticate. A caller is either a signed Mini App payload or a shared service token plus a Telegram user ID header. An Android app has neither, and an MCP server acts for a person it can't represent. Nothing else on this page is reachable until identity stops being Telegram-shaped.

Reads have side effects. Every search writes an attempt row for metrics and pushes misses onto a review queue. An MCP server answering "how much protein is in cottage cheese" would pollute both. Search should be free to call.

Product policy is baked into the wire format. A failed search returns 422 instead of an empty list. Weigh-ins are exposed only as a 7-day rolling average, because the original spec said never show day-over-day deltas — so no client can ever draw a different chart. The day view welds entries, totals and targets into one object. These are display rules living in the server.

The shape to move to

Four resources and two verbs' worth of cleverness. Anything a client can compute from what it already has, it computes.

Entries — the centre of gravity

One endpoint accepts three ways of saying how much of what, and the first one needs no database at all:

POST /v1/entries
{ "name": "мамина запіканка", "grams": 250,
  "nutrition": { "kcal": 180, "protein": 9, "fat": 7, "carbs": 21 } }

POST /v1/entries
{ "food_id": 412, "grams": 150 }

POST /v1/entries
{ "food_id": 412, "portion_id": 9, "count": 2 }

The first form is the headline feature. It creates no food record, requires no search, and is the thing FatSecret makes you work around. The server still snapshots the numbers onto the entry, so a later catalogue correction never rewrites a day you already logged — that behaviour stays exactly as it is.

Reads become a plain range query returning rows, with totals as an opt-in. A day view, a week chart and a month export are then the same call with different bounds, and "repeat yesterday" is a client reading one range and posting it back.

Foods — a cache, not a gate

Creating a food takes nutrition values and a name. That is the whole requirement. No searching for something similar, no borrowing someone else's row, no taxonomy to satisfy.

Two further moves worth making while you're there. Portions get stable IDs instead of being referenced by name string, so a client can offer "тарілка" as a button without string-matching. And an entry you logged ad-hoc can be promoted into a food in one call, which is the natural path: log it the first time, keep it the second time.

Search splits from interpretation. A plain query returns ranked rows and an empty array when nothing matches. A separate parse endpoint takes "варена курка 150г" and returns candidates plus the quantity it pulled out of the phrase — for the chat client and the MCP, which genuinely want that, and for nobody else.

Composite foods the nice stuff

A food defined as a list of ingredients and a yield weight, with per-100 g values computed server-side. Cook a pot of something, define it once, log portions of it for a week. This is the feature FatSecret has and makes unpleasant, and it's cheap here because ingredient rows and gram-based scaling already exist.

Targets and weights stop being opinions

Target calculation becomes a stateless call: send the body numbers, get back maintenance, a suggested deficit and a protein figure. Storing them is a separate, dumb write. A client can show the arithmetic before an account exists, and recompute whenever weight changes.

Weigh-ins return as recorded, with aggregation as a query parameter. The no-deltas rule moves to where it belongs — the client that decided it.

One scheme, three issuers

Every request carries Authorization: Bearer <token>. Nothing else. Tokens come from wherever the client can get one:

ClientGets a token by
MCP, scripts, crona long-lived key you create and paste
Telegram bot and Mini Appexchanging a signed launch payload for a token
Androida device login, or the same pasted key while it's just you

Telegram stops being an identity and becomes an identity linked to an account. That one change is what lets the same logged meal appear in the bot and the phone.

Cross-cutting, all missing today

  • Pagination on every list. There is none anywhere right now, and the catalogue is already 3,600 rows.
  • Idempotency keys on entry creation. A phone retrying on bad signal currently logs the meal twice.
  • Errors carry a developer message alongside the machine code. An MCP surfaces failures to a human, and a bare code tells them nothing. Clients still translate by code.
  • Explicit dates in requests, with the user's timezone used only to resolve "today" when a client asks for it.

Decisions to make

Licence posture for search and MCPblocks: search endpoints, MCP

3,122 of 3,603 foods come from a retailer whose terms forbid reproduction. Today the API only ever returns one resolved row, which is defensible. A paginated search endpoint is much closer to the line, and an MCP hands rows to a model vendor. The search work waits on this.

Identity modelblocks: phases 2-6

Every caller today is a signed Telegram payload or a service token plus a Telegram user ID header. Android has neither, and an MCP acts for a person it cannot represent. Nothing non-Telegram is testable until this lands.

What the review queue is forblocks: catalogue expansion loop

2,190 open items, almost all ingest rejections rather than food you failed to log. The PRD gave this queue the job of driving catalogue expansion from your real misses, and it is not currently doing that job.

Сільпо adapter

The slug fix is correct and every endpoint answers in under 0.2s by hand, but in-process it crawls at roughly one request per 30 seconds and has never staged a row. Zakaz.ua already covers Ukrainian retail with 3,122 working rows.

Open Food Facts

Never run once. It is the barcode backbone in the PRD and one of only three redistributable sources, so it is also the answer to the licence question if you pick the filtered option.

Bot view-model endpoints during migration

The day view, repeat-yesterday, recents and weight trend are all replaced by range queries in the redesign. The bot depends on all four today.

Composite foods versus MCP

Recipes are independent of the redesign and cheap, since gram-based scaling already exists. The MCP is the client that proves the API is genuinely universal.

Semantic search

Deferred as of this session, recorded so the reasoning survives: trigram plus curated aliases already handles your real queries, and the value is cross-lingual and descriptive search for agent clients.

Already settled

Postgres over SQLite, because the API, scheduler and ingest workers all write concurrently. Compose on one host over Kubernetes. A hand-written OpenAPI spec over generated annotations. Licence class and confidence declared by each adapter rather than by a switch in the shared normalizer. The curated catalogue embedded in the binary. Nutrition snapshotted onto entries at save time.

Order of work

1. Identity blocker

Accounts, bearer tokens, Telegram demoted to a linked identity. Nothing else can be built or tested by a non-Telegram client until this lands.

2. Entries accept inline nutrition

The smallest change with the largest payoff, and the reason for the project. One endpoint, one branch, no new tables. After this the app is already more useful to you than FatSecret for the case that annoys you.

3. Foods become a normal resource

Create from values, search split from parse, stable portion IDs, promote-an-entry-to-a-food. Delete the resolve endpoint once the chat client moves to parse.

4. Delete the view models

Day view, repeat-yesterday, recents, the weight trend. Each is replaced by a range query the clients already need. This is the phase that shrinks the surface instead of growing it.

5. Composite foods

Ingredients plus yield, values computed on write. Independent of everything above.

6. MCP

If phases 1–4 land properly this is a declarative table of operations over the REST surface, the same shape as the FatSecret wrapper. If it turns out to need custom logic, that's the signal the API is still carrying a client's opinions.

What explicitly does not change

Nutrition stays per 100 g on foods and absolute on entries. Entries keep snapshotting values at save time. Portion-to-gram conversion stays server-side. The ingestion pipeline, the confidence ladder that stops a scraped row overwriting a hand-verified one, and the Ukrainian alias matching are all untouched — that catalogue is the part FatSecret can't give you, and none of this redesign touches how it's built.

The clients going stale is fine and expected. The bot will keep working against the old endpoints until phase 4 removes them, and by then the shape it should move to already exists.
